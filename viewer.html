World-frame coordinates in metres (grid lines every 20m × 15m) — sense::to_detection() output, before any tracking. Bright dots are this cycle; faint dots are the last ~1s, fading out, so you can see which way things are moving. Raw detections have no ID from cycle to cycle, so their trail is a fading cloud, not a line. Fused tracks (yellow rings) do have a stable ID, so theirs draws as a real connected trail. Fusion

main.cpp fusion thread + sensors.hpp to_detection() — merges 3 sensor streams into one detection list

detection volume vs. tracks produced

"Total detections" is every radar+camera+lidar measurement merged this cycle (main.cpp:150-155); "confirmed tracks" is what Tracker::update() distilled them into. A wide, steady gap between the two lines is fusion doing its job — many noisy readings, few stable beliefs.

cumulative (this run)

fusion cycles run—
One cycle = one drain() of the BlockingQueue, event-driven (not fixed-rate) — it wakes whenever any sensor frame arrives, up to every 20 ms. Merging itself has no separate "algorithm": to_detection() just normalizes each sensor's raw type into a common Detection struct; tracker.hpp:194 is what actually associates them into tracks.

Tracker

tracker.hpp — per-object Kalman filters, data association, confirm/prune lifecycle
Four small charts, each answering one question about the tracker, in order: how many objects does it believe in, is it confident about them, is that confidence trustworthy, and how many sensors agree.

1. tracks & confidence

How many objects are currently confirmed, and how sure the filter is about their position (σ, in metres — smaller is more confident). σ should fall as a track accumulates hits.

2. hits vs. misses

Average, per confirmed track, how many cycles it was actually detected in (hits) vs. cycles it was predicted-but-missed (misses). Misses rising toward hits means a track is about to be pruned.

3. is that confidence trustworthy?

σ (from chart 1) is what the filter believes about its own error. "actual error" is the real distance from each track to the nearest ground-truth obstacle — something the filter never sees. The two lines should track each other; σ sitting well below actual error means the filter is overconfident.

4. sensor agreement

Confirmed tracks, grouped by how many different sensor types (radar/camera/lidar) have ever hit them. Confirmation requires 2, so "1 sensor kind" should stay near zero — if it rises, the confirmation gate isn't working.

Planner

planner.hpp — lattice of candidate offsets, scored against predicted obstacle motion

planning stats

Cost spikes when an obstacle gets close (the w_clearance penalty in build_and_score); target speed should dip in lockstep, since both come from the same min_clearance. Lateral offset shows which of the 5 candidate lanes (−3.5, −2, 0, +2, +3.5 m) actually got chosen each cycle.

cumulative (this run)

plans computed—
Runs at a fixed 10 Hz (kPlanPeriod in main.cpp), independent of the fusion rate — each cycle forks 5 std::async tasks, one per candidate offset, and keeps the minimum-cost path.

Control

controller.hpp — pure pursuit (steering) + PID (speed), turning the plan into a Control command

speed tracking

Ego speed chasing the planner's target speed is the PID loop in controller.hpp doing its job — a widening, sustained gap usually means the gains (kp/ki/kd) or the accel clamp in vehicle.hpp can't keep up.

control effort

The actual Control{accel, steer} sent to World::step() each cycle. Steer sign flips as pure pursuit tracks the lookahead point around the oval; accel should go negative (braking) right when the planner's target speed chart drops.

ride comfort

Jerk is d(accel)/dt — the thing passengers actually feel, not raw accel. Lateral accel is ego speed × yaw rate (from consecutive ego.yaw), a proxy for cornering g-force. Sharp spikes in either usually line up with a planner lane-change (the offset chart, Planner section) landing on a controller that has to react in one 20 ms control tick instead of smoothing across several.

Thread Timing

cross-cutting — conc::Stats counters differentiated over time, checking main.cpp's seven std::jthreads actually hit their target rates

measured rate vs. nominal (Hz)

Each line is d(counter)/dt between consecutive recorded frames (render runs at 12 Hz, so this is a ~83 ms window average, not instantaneous — expect noise, not a flat line). Dashed reference: radar 20, camera 15, lidar 10, control 50, sim 100 Hz. A line sagging persistently below its nominal value — not just noisy around it — means that thread is being starved: CPU contention, a lock held too long, or a body that overruns its own period (run_at_rate can't catch up once behind).

Safety & Outcome

cross-cutting — ego vs. ground-truth obstacles (obs[]), independent of what the tracker believed; this is "how close did we actually come," not "what did fusion see"

closing distance & time-to-collision, nearest obstacle

Distance is centre-to-centre to the nearest obs[], minus its radius — ground truth, not the planner's min_clearance (which only sees confirmed tracks and is what the planner actually reacted to). TTC is distance ÷ closing rate, clamped to 15s and blank while opening. Compare the two: the planner's clearance chart (Planner section) reacting to something this chart doesn't yet show as urgent is worth investigating.
