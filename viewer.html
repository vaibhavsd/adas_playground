Fusion

main.cpp fusion thread + sensors.hpp to_detection() — merges 3 sensor streams into one detection list

detection volume vs. tracks produced

"Total detections" is every radar+camera+lidar measurement merged this cycle (main.cpp:150-155); "confirmed tracks" is what Tracker::update() distilled them into. A wide, steady gap between the two lines is fusion doing its job — many noisy readings, few stable beliefs.

cumulative (this run)

fusion cycles run—
One cycle = one drain() of the BlockingQueue, event-driven (not fixed-rate) — it wakes whenever any sensor frame arrives, up to every 20 ms. Merging itself has no separate "algorithm": to_detection() just normalizes each sensor's raw type into a common Detection struct; tracker.hpp:194 is what actually associates them into tracks.

Tracker

tracker.hpp — per-object Kalman filters, data association, confirm/prune lifecycle

track confidence

σ is the Kalman position uncertainty (Track::pos_sigma) — it should trend down as a track accumulates hits. "confirmed tracks" only counts tracks that passed is_confirmed(); tentative tracks never reach this file at all (see docs/tracker-explainer.html § Pipeline).

sensor agreement (confirmed tracks, per cycle)

Counts confirmed tracks by how many distinct sensor kinds (popcount of sensor_mask) ever hit them. Since confirm_sensors=2 by default, the "1 sensor kind" line should stay near zero among confirmed tracks — seeing it rise is a sign the confirmation gate isn't doing its job.

Planner

planner.hpp — lattice of candidate offsets, scored against predicted obstacle motion

planning stats

Cost spikes when an obstacle gets close (the w_clearance penalty in build_and_score); target speed should dip in lockstep, since both come from the same min_clearance. Lateral offset shows which of the 5 candidate lanes (−3.5, −2, 0, +2, +3.5 m) actually got chosen each cycle.

cumulative (this run)

plans computed—
Runs at a fixed 10 Hz (kPlanPeriod in main.cpp), independent of the fusion rate — each cycle forks 5 std::async tasks, one per candidate offset, and keeps the minimum-cost path.
🎮

Control

controller.hpp — pure pursuit (steering) + PID (speed), turning the plan into a Control command

speed tracking

Ego speed chasing the planner's target speed is the PID loop in controller.hpp doing its job — a widening, sustained gap usually means the gains (kp/ki/kd) or the accel clamp in vehicle.hpp can't keep up.

control effort

The actual Control{accel, steer} sent to World::step() each cycle. Steer sign flips as pure pursuit tracks the lookahead point around the oval; accel should go negative (braking) right when the planner's target speed chart drops.
