Overview

Day 1 — geometry.hpp — "Every ADAS stack is secretly a geometry library with opinions."

What these three functions are for

Three small free functions, all defined in the first ~100 lines of the whole codebase, and all still doing work on the very last day (Day 10, main.cpp). Between them they answer two questions every other module needs answered constantly:
  1. to_ego_frame / to_world_frame — "where is that point, relative to the car?" and its inverse, "I have a point relative to the car, where is that in the world?" Sensors, the controller, and the renderer all ask one of these dozens of times per cycle.
  2. distance_to_segment — "how close does object X get to this piece of the planned path?" — the one line of math the planner's entire collision check is built on.
None of the three do anything exotic — a rotation, a subtraction, a clamp — but seeing where they're called (six files, listed below) is the fastest way to understand how the whole stack shares one small geometric vocabulary instead of every module inventing its own.

World frame vs. ego frame

The two coordinate systems everything in this repo is expressed in

Two frames, one convention each

World frame: fixed, global — the track's own coordinates. Every Obstacle, every Pose, everything in a recorded run.jsonl frame is in world frame.
Ego frame: attached to the car, moves and rotates with it. Origin at the car's position; +x points where the car is facing (forward), +y points left. A point at ego-frame (5, 0) is always "5 m directly ahead of the car," no matter which way the car is pointed in the world.
Both pictures show the same physical situation — the numbers match the worked example below. Why bother with a second frame at all? Because "is that obstacle in front of me, within my field of view, within braking distance" are all questions that are trivial in ego frame (check rel.x, check rel.norm(), check rel.angle()) and comparatively awkward in world frame, where you'd have to subtract off the car's heading by hand every single time.

to_ego_frame(world_pt, ego)

"Where is this world point, relative to the car?"

The math

Two steps: translate so the car is at the origin, then rotate by minus the car's heading so "forward" lines up with the ego-frame +x axis.
$$ p_{\text{ego}} = R(-\psi)\,(p_{\text{world}} - p_{\text{ego,pos}}) $$
where $\psi$ is ego.yaw and the rotation matrix is the standard 2D one:
$$ R(\theta) = \begin{pmatrix} \cos\theta & -\sin\theta \\ \sin\theta & \cos\theta \end{pmatrix} $$ 
[[nodiscard]] inline Vec2 to_ego_frame(Vec2 world_pt, const Pose& ego) noexcept {
    return (world_pt - ego.pos).rotated(-ego.yaw);
}
rotated(a) (geometry.hpp:79) is where $R(\theta)$ actually lives — {c*x - s*y, s*x + c*y} with c=cos(a), s=sin(a) is that matrix, written out. Order matters: subtract the position first, then rotate — rotating first would spin the car's own position around the world origin instead of around itself.

Every single one of those call sites is really asking the same question — "how does this look from the car's point of view" — just for a different purpose (can a sensor see it, how do I steer toward it, does this pixel belong to the car). One function, one idea, reused four different ways.

to_world_frame(ego_pt, ego)

The inverse — "I have a point relative to the car, where is it in the world?"

The math

Exactly the two steps of to_ego_frame, reversed: rotate first, then translate.
$$ p_{\text{world}} = R(\psi)\,p_{\text{ego}} + p_{\text{ego,pos}} $$ 
[[nodiscard]] inline Vec2 to_world_frame(Vec2 ego_pt, const Pose& ego) noexcept {
    return ego_pt.rotated(ego.yaw) + ego.pos;
}
Rotating by +ego.yaw (not -ego.yaw) and doing it before the translation is what makes this the true inverse of to_ego_frame — swap either the sign or the order and round-tripping a point through both functions would silently return the wrong answer instead of the original point.

Where it's actually called

Every real usage is the same shape: a sensor measures something in its own ego-relative polar coordinates (range + bearing — how sensors actually report in the real world), and to_detection() has to turn that back into a world-frame position before it's usable by tracking, which only ever reasons in world frame.
FileWhat's being converted
sensors.hpp:246Radar's (range, bearing) → a world-frame position, via Vec2{range,0}.rotated(bearing) (build the ego-frame offset first) then to_world_frame.
sensors.hpp:254Camera's (est_range, bearing) → world frame, same pattern.
sensors.hpp:259Lidar already reports an ego-frame centroid directly (no polar conversion needed first) — straight into to_world_frame.
This is the moment sensor fusion becomes possible at all: radar, camera and lidar each see the world through their own, differently-shaped keyhole, but the instant to_detection() calls to_world_frame, all three land in the same shared coordinate system — which is the only reason tracker.hpp can compare a radar return to a lidar cluster in the first place.

Worked example 1 — the round trip (clean 90°)

This is exactly what tests/test_main.cpp checks (line 39-42), so you can run ./build/adas_tests and watch it pass. 

ego.pos = (10, 10),  ego.yaw = 90°  (π/2 rad — facing +y)
world_pt = (10, 15)                 (5 m due north of the car)

to_ego_frame: subtract, then rotate by −90°.

$$ \begin{aligned} \Delta &= (10,15) - (10,10) = (0, 5) \\ p_{\text{ego}} &= R(-90°)\,(0,5) = (5, 0) \end{aligned} $$

Makes sense: the car is facing +y (north), and the point is 5 m north of it — so "5 m straight ahead" is exactly (5, 0) in ego frame. That's the whole point of the frame: "ahead" is always +x, no matter which way north actually points.

to_world_frame: rotate that result by +90°, then add the car's position back.

$$ \begin{aligned} R(90°)\,(5,0) &= (0, 5) \\ p_{\text{world}} &= (0,5) + (10,10) = (10, 15) \end{aligned} $$

Back to exactly where we started — which is the definition of an inverse, and the only thing the unit test actually asserts.

Worked example 2 — a general yaw (no clean angles this time)

90° is a convenient teaching example, but it's also special: the rotation just swaps and negates an axis, no actual trigonometry visible. Here's the same two functions with a yaw that isn't a multiple of 90°, so cos/sin actually show up in the arithmetic. 

ego.pos = (0, 0),  ego.yaw = 30°   (π/6 rad)
world_pt = (10, 0)                  (10 m due east — along world +x)

to_ego_frame: Δ = (10,0) (ego is at the origin here, so no translation to speak of), then rotate by −30°.

$$ \begin{aligned} R(-30°)\,(10,0) &= (\cos(-30°)\cdot 10 - \sin(-30°)\cdot 0,\ \ \sin(-30°)\cdot 10 + \cos(-30°)\cdot 0) \\ &= (0.8660 \times 10,\ -0.5 \times 10) = (8.660,\ -5.000) \end{aligned} $$

The point is 10 m away either way (rotation preserves distance — $\sqrt{8.660^2+5.000^2}=10$), but the car is turned 30° away from pointing straight at it, so in ego frame the point reads as mostly-ahead ($x=8.66$) and off to the right ($y=-5$, and recall +y is left — negative is right).

to_world_frame: rotate (8.660, −5.000) by +30° this time, then add ego.pos = (0,0).

$$ \begin{aligned} R(30°)\,(8.660,-5.000) &= (0.8660\times 8.660 - 0.5\times(-5.000),\ \ 0.5\times 8.660 + 0.8660\times(-5.000)) \\ &= (7.500 + 2.500,\ \ 4.330 - 4.330) = (10.000,\ 0.000) \end{aligned} $$

Same result as the 90° example: round-tripping through to_ego_frame then to_world_frame lands exactly back on the original point, for any yaw — not just the convenient one.

distance_to_segment(p, a, b)

"How close does point p get to the line segment from a to b?" — not the infinite line, the segment

The math — project, clamp, measure

Project $p$ onto the infinite line through $a$ and $b$, expressed as a parameter $t$ (0 at $a$, 1 at $b$). Clamping $t$ to $[0,1]$ is what turns "distance to a line" into "distance to a segment" — without the clamp, a point off the end of the segment would incorrectly measure against a point that isn't actually on it.
$$ t = \operatorname{clamp}\!\left(\frac{(p-a)\cdot(b-a)}{\lVert b-a \rVert^2},\ 0,\ 1\right) \qquad \text{closest} = a + t\,(b-a) $$
$$ \text{distance} = \lVert p - \text{closest} \rVert $$
[[nodiscard]] inline double distance_to_segment(Vec2 p, Vec2 a, Vec2 b) noexcept {
    const Vec2 ab = b - a;
    const double len2 = ab.norm2();
    if (len2 < 1e-12) return distance(p, a);      // a == b: segment has zero length
    const double t = std::clamp((p - a).dot(ab) / len2, 0.0, 1.0);
    return distance(p, a + ab * t);
}
The len2 < 1e-12 guard handles the degenerate case where a and b are (numerically) the same point — dividing by a near-zero len2 would otherwise produce garbage or a division by zero.

Worked example

a = (0, 0),  b = (10, 0)     (a 10 m path segment along the x-axis)
p = (4, 3)                   (an obstacle 4 m along, 3 m off to the side)
$$ \begin{aligned} ab &= (10, 0), \quad \lVert ab \rVert^2 = 100 \\ t &= \operatorname{clamp}\!\left(\frac{(4,3)\cdot(10,0)}{100},\ 0,\ 1\right) = \operatorname{clamp}(0.4,\ 0,\ 1) = 0.4 \\ \text{closest} &= (0,0) + 0.4\,(10,0) = (4, 0) \\ \text{distance} &= \lVert (4,3) - (4,0) \rVert = 3.0 \text{ m} \end{aligned} $$

Now push the obstacle past the end of the segment — p = (13, 3). The raw projection would give $t = 1.3$, but the clamp pins it to $t=1$, so the closest point becomes $b=(10,0)$ and the distance is $\sqrt{3^2+3^2} \approx 4.24$ m, not the (wrong) 3 m you'd get from measuring against the infinite line.

Why a segment, not a point

The one real caller — planner.hpp's collision check — and the bug that explains why it's written this way

planner.hpp:188 — clearance to each waypoint segment

The lattice planner scores a candidate path by checking, for every waypoint, how close the predicted position of every tracked obstacle gets. The naive version of this check would just measure distance to each waypoint (a point). This code deliberately measures against the segment from the previous waypoint to this one instead: 
const Vec2   from = (k == 0) ? pic.ego.pos : p.points[k - 1];
for (const auto& rt : rts) {
    const Vec2   predicted = predict(rt, t);
    const double clr = geo::distance_to_segment(predicted, from, p.points[k]) - bubble;
    ...
}

The bug this fixed

Straight from the comment above that loop in the source:
"With 1.5 m spacing and a 1 m/step relative motion, a point-only check can step straight over a collision (it did — that bug is how this comment got written)."
The failure mode: waypoints are sampled every 1.5 m along the path, but a fast obstacle can close more than 1 m of distance between two consecutive waypoints. If you only check "how far is the obstacle from waypoint k" and "how far from waypoint k+1", it's entirely possible for the obstacle to cross the car's actual path in between — close to both sampled points, yet the straight-line segment connecting them still runs right through it — and a point-only check would never notice. Checking distance to the segment instead of the two endpoints catches exactly that case, because the segment is the path the car will actually drive, not just the points it happens to be sampled at.
