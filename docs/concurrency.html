Overview

Day 3 — concurrency.hpp — "Before we build the world, we build the phone lines."

What this file is

Five small thread-safety primitives, written before anything that needs them exists (the world, the sensors, the tracker are all Day 4+) — because every one of the eight threads main.cpp eventually spins up (Day 10) needs a safe way to hand data to the others, and this file is the entire menu of options:
TypeShapeUsed for
BlockingQueue<T>many-to-one, batchsensor frames → fusion
Latest<T>one-to-many, newest-winsfused picture → planner & controller
Shared<T>one-to-one/few, plain boxpath → controller, control → world
EventLogmany-to-one, singletonevery module logs into one place
Statsmany-to-one, counters onlyper-thread cycle counts, lock-free
Plus one function, run_at_rate(), that isn't about sharing data at all — it's what makes every one of those eight threads actually tick at a steady rate in the first place.
None of these are exotic. There's no lock-free ring buffer, no custom atomics dance beyond one textbook release/acquire pair. The lesson here isn't "concurrency is hard, look at this clever trick" — it's "here are the four or five shapes that cover almost every real producer/consumer problem, pick the right one and the rest is standard library."

BlockingQueue<T>

Many producers, one consumer, "give me everything that's arrived" instead of one-at-a-time

Why drain-all instead of pop-one

The obvious queue API is push() / pop() — one item at a time. This queue deliberately doesn't offer pop() at all. Its only consumer is the fusion thread, and fusion doesn't want "the next detection," it wants every detection that arrived since the last cycle, all at once, so it can process them as one batch: 
void push(T item) {
    { std::lock_guard lk(m_); items_.push_back(std::move(item)); }
    cv_.notify_one();
}

std::vector<T> drain(std::chrono::milliseconds timeout) {
    std::unique_lock lk(m_);
    cv_.wait_for(lk, timeout, [&] { return !items_.empty() || closed_; });
    std::vector<T> out;
    out.swap(items_);   // O(1): steal the buffer, leave an empty one behind
    return out;
}
swap instead of = items_; items_.clear() is the small trick worth noticing: it's a pointer/size swap, not a copy of every pending item, and it leaves items_ as a valid empty vector for the next round of pushes.
concurrency.hpp:79-111

Why unique_lock here but lock_guard elsewhere

push() and close() use the plain lock_guard — lock, do one thing, unlock. drain() needs unique_lock specifically because condition_variable::wait_for has to be able to unlock the mutex while it waits (so producers can still push()) and re-lock it the instant it wakes up — a capability lock_guard doesn't have by design (it's RAII-simple, on purpose, and can't be unlocked early).
concurrency.hpp:94 vs. concurrency.hpp:84,102

Why notify outside the lock

push() closes its lock scope with a bare { ... } block before calling cv_.notify_one(). If the notify happened while still holding the lock, the woken consumer thread would immediately try to re-lock the same mutex and block again until the producer's scope actually ends — a real (if usually tiny) contention window, avoided here for free by just moving one line outside the braces.

Where it's actually used

Exactly one queue, in the whole program. Three sensor threads push into it; one fusion thread drains it: 
adas::conc::BlockingQueue<adas::sense::SensorFrame> queue;         // main.cpp:106

// radar / camera / lidar threads, each at their own rate:
queue.push(sensor->capture(world.snapshot()));                    // main.cpp:138

// fusion thread, event-driven — wakes whenever anything arrives:
while (!st.stop_requested()) {
    auto frames = queue.drain(20ms);                               // main.cpp:147
    if (frames.empty()) continue;
    ...
}

// shutdown:
queue.close();                                                     // main.cpp:210
That 20ms timeout is a ceiling, not a rate — drain() returns the moment anything is pushed (radar alone pushes every 50 ms, camera every ~67 ms, lidar every 100 ms), so fusion is event-driven in practice and only ever blocks for the full 20 ms if every sensor happens to go quiet.

Worked example — one drain() cycle

A slice of real timing, radar (20 Hz → 50 ms) and camera (15 Hz → ~67 ms) both mid-flight:

t=0ms     fusion calls drain(20ms), queue is empty → blocks
t=12ms    radar thread:  queue.push(radar_frame)   → cv_.notify_one()
t=12ms    fusion wakes immediately (well under the 20ms timeout),
          swaps out items_ = [radar_frame], returns it
t=12ms    fusion:  drain() returned [radar_frame]  → tracker.update([radar_frame])
t=12ms    fusion calls drain(20ms) again, queue is empty → blocks
t=31ms    camera thread: queue.push(camera_frame)  → cv_.notify_one()
t=31ms    fusion wakes, drain() returns [camera_frame]

If instead radar and camera had landed 1ms apart (t=12ms and t=13ms), and fusion happened to be slow to wake, one drain() call would return both frames in the same std::vector — that's the entire point of batching: fusion never has to care how many sensors fired in a given window, it just processes "whatever showed up."

Latest<T>

One writer, many readers, "give me the newest value" — old ones are simply gone

Why shared_mutex

A plain std::mutex only ever allows one thread in at a time, reader or writer. Latest uses std::shared_mutex instead so that N readers can all proceed concurrently, and only the one writer needs exclusive access: 
void publish(T value) {
    { std::scoped_lock lk(m_); value_ = std::move(value); }   // exclusive lock
    version_.fetch_add(1, std::memory_order_release);
}

T read() const {
    std::shared_lock lk(m_);   // shared lock — many readers at once
    return value_;             // copy out; the lock ends here
}
In this codebase that matters concretely: the planner thread and the controller thread both call picture.read() independently, at different rates (10 Hz vs. 50 Hz) — with a plain mutex, one would occasionally have to wait on the other for no real reason. With shared_mutex, they never block each other; only publish() (the fusion thread, once per cycle) ever needs exclusive access.
concurrency.hpp:125-149

The lock-free "has anything happened yet" check

version_ is a plain std::atomic<uint64_t>, incremented on every publish. Reading it needs no lock at all — so any thread can cheaply ask "is there anything to read yet?" before paying for a real read() (which copies the whole value out): 
if (picture.version() == 0) return;   // nothing fused yet — main.cpp:173, 183
Without this, the planner and controller threads would have to call the full read() every cycle from the moment they start, get back a default-constructed FusedPicture{}, and have to separately check that for emptiness — this is simpler and cheaper.

The memory-order comment, unpacked

The header comment calls this "belt-and-braces" — worth understanding literally. memory_order_release on the writer's fetch_add and memory_order_acquire on the reader's load together guarantee: if a reader observes version N, it is also guaranteed to see every write that happened before version N was stored — no reordering can let the reader see the new version number but a stale value_.
Here, the shared_mutex around value_ already provides that guarantee on its own (acquiring any mutex is itself an acquire-fence, releasing one is a release-fence) — so the explicit memory orders on version_ are technically redundant with the lock that's already there. They're included anyway because version() is read completely outside any lock (that's the whole point of it being cheap), and the acquire/release pairing is what makes that safe on its own, independent of the mutex. It's the idiom worth memorizing, not just an artifact of this one class.

Shared<T>

When you don't need multiple readers or a version counter — just a lock and a box

The whole class

template <typename T>
class Shared {
public:
    void set(T v) { std::scoped_lock lk(m_); value_ = std::move(v); }
    T    get() const { std::scoped_lock lk(m_); return value_; }
private:
    mutable std::mutex m_;
    T                  value_{};
};
No shared_mutex, no version counter, no condition variable — deliberately the simplest thing that could work. Choosing this over Latest is a judgment call about read pressure: Path and Control each have exactly one reader (the controller reads the path; the world reads the control), so there's no reader contention to optimize away with a shared_mutex — it would just be extra machinery with nothing to buy.
concurrency.hpp:154-163

Where it's actually used

adas::conc::Shared<adas::plan::Path>    path;      // main.cpp:111
adas::conc::Shared<adas::sim::Control>  command;   // main.cpp:112

path.set(planner->plan(picture.read(), world.course()));    // planner thread, 10 Hz — main.cpp:174
command.set(controller.compute(pic.ego, pic.ego_speed, path.get(), dt));  // control thread, 50 Hz — main.cpp:185
world.step(command.get(), dt);                               // sim thread, 100 Hz — main.cpp:126
Notice the asymmetry with Latest: picture is written by one thread and read by three (planner, controller, render), so it earns the shared_mutex. path and command are each written by one thread and read by exactly one other, so Shared is the right-sized tool — using Latest there wouldn't be wrong, just unnecessary.

EventLog

A thread-safe singleton logger — every module posts into the same tail(), no wiring required

The Meyers singleton

static EventLog& instance() {
    static EventLog log;   // function-local static
    return log;
}
Since C++11, initialization of a function-local static is guaranteed thread-safe by the language itself — if two threads call instance() for the first time simultaneously, the compiler-generated code ensures the constructor runs exactly once and every caller gets the same, fully-constructed object. No manual std::once_flag, no double-checked locking pattern needed; this is the whole reason "Meyers singleton" (named for Scott Meyers, who popularized it) is the standard way to write one in modern C++.
concurrency.hpp:174-177

source_location instead of __FILE__/__LINE__

void post(std::string msg,
          std::source_location loc = std::source_location::current()) { ... }
std::source_location::current() as a default argument captures the file and line of the call site — not of this function's own definition — because default arguments are evaluated at each call. Every module in this codebase can write EventLog::instance().post("...") with zero boilerplate and get an accurate tracker.hpp:226-style tag for free, where the old C idiom needed an explicit __FILE__, __LINE__ macro pair threaded through every call.

Stats

Lock-free counters — no mutex needed when all you ever do is increment and read

Why no mutex at all

struct Stats {
    std::array<std::atomic<int>, 3> sensor_frames{};  // indexed by SensorKind
    std::atomic<int> fusion_cycles{0};
    std::atomic<int> plans{0};
    std::atomic<int> control_ticks{0};
    std::atomic<int> sim_ticks{0};
    std::atomic<int> render_frames{0};
};
std::atomic<int>::operator++ is itself an atomic read-modify-write — no two threads incrementing the same counter can ever race and lose an update, with no lock involved. This works specifically because every field here is "increment it, read it later" — there's never a need to update two counters together as one atomic unit (that would need a real lock), so a struct of independent atomics is the simplest thing that's still fully correct.
concurrency.hpp:211-218

One counter, seven writers, one reader

Every field is incremented by a different thread, all sharing the one Stats stats; instance declared in main(): 
++stats.sim_ticks;                                              // sim thread     — main.cpp:127
++stats.sensor_frames[static_cast<std::size_t>(f.kind)];        // fusion thread  — main.cpp:155
++stats.fusion_cycles;                                          // fusion thread  — main.cpp:165
++stats.plans;                                                  // planner thread — main.cpp:175
++stats.control_ticks;                                          // control thread — main.cpp:186
++stats.render_frames;                                          // render thread  — main.cpp:200
The render thread reads all of them every frame (the header/footer counters you see in the terminal and in run.jsonl's stats{} object), and main() reads the final totals once at shutdown for the post-race summary. sensor_frames being incremented by fusion rather than by each sensor thread itself is worth noticing: fusion counts a frame once it's actually been drained and processed, not just pushed — so this counter reflects work done, not just work queued.

run_at_rate()

"The heartbeat of every thread in this project" — not a data-sharing primitive, a timing one

sleep_until vs. sleep_for

The naive fixed-rate loop calls sleep_for(period) after each iteration. That's wrong for anything that needs a steady average rate: if the body itself takes time to run, sleep_for only waits period after the body finishes — so every iteration's total cost is body_time + period, and the loop drifts later and later relative to a true fixed schedule. 
template <std::invocable<double> Body>
void run_at_rate(std::stop_token st, std::chrono::milliseconds period, Body&& body) {
    auto next = Clock::now();
    auto last = next;
    bool first = true;
    while (!st.stop_requested()) {
        const auto now = Clock::now();
        const double dt = first ? std::chrono::duration<double>(period).count()
                                : std::chrono::duration<double>(now - last).count();
        first = false;
        last = now;
        body(dt);
        next += period;                    // absolute deadline, not "now + period"
        std::this_thread::sleep_until(next);
    }
}
next += period advances an absolute deadline that was fixed before the body ever ran. If the body happens to run long one cycle, sleep_until(next) simply returns almost immediately (or not at all, if next is already in the past) instead of adding a full extra period on top — the schedule can catch up, it never accumulates drift.
concurrency.hpp:230-245

Worked example — a 100 Hz loop with one slow cycle

period = 10ms (this is literally kSimPeriod, main.cpp:48). Three iterations, the second one's body runs long:

iteration 1: next = t0 + 10ms.  body takes 2ms.   sleep_until(t0+10ms) waits  8ms. starts at t0+10ms.  ON SCHEDULE
iteration 2: next = t0 + 20ms.  body takes 14ms!  sleep_until(t0+20ms) is already PAST → returns immediately. starts at t0+24ms. LATE this once
iteration 3: next = t0 + 30ms.  body takes 2ms.   sleep_until(t0+30ms) waits  4ms (30 - 24 - 2). starts at t0+30ms.  BACK ON SCHEDULE

With sleep_for(10ms) instead — same three body times, traced independently — the drift never recovers: iteration 2 starts at t0+12ms (already 2 ms late, from body 1's time alone — sleep_for adds lateness even when the body finishes under the period, because it never looks at the clock, only at how long it's asked to sleep after whatever just happened). Iteration 3 starts at t0+36ms (16 ms late — body 2's full 14 ms stacked on top, not just the 4 ms it ran over). Iteration 4 starts at t0+48ms (18 ms late). Every cycle's body time becomes permanent lateness, whether or not that cycle happened to run over. sleep_until's iteration 4, by contrast, lands exactly on t0+30ms — dead on the ideal grid — because only the one cycle that actually overran (iteration 2) ever cost it anything.

Why std::invocable<double>

The template parameter is constrained to lambdas callable with one double argument (the computed dt). Without the concept, passing a lambda with the wrong signature — say, one that takes no arguments — would fail deep inside the template instantiation with a wall of unreadable errors about body(dt) not being callable. With the concept, the compiler rejects it right at the call site with a message that names the actual constraint that failed.
