🧵C++ Threading: Complete Beginner's Guide

Goal: Understand threads, synchronization primitives, and how to write safe concurrent code.

📚Part 1: Threading Fundamentals

What is a Thread?

A thread is a lightweight execution path within a process. Multiple threads share the same memory space but run code independently and (on multi-core CPUs) in parallel.

Key idea: While Thread A is executing a function, Thread B can simultaneously execute a different function. They can interfere with each other if they access the same data—that's why synchronization matters.

Single-threaded program (old way):
┌──────────────────────────────────────┐
│ Main Thread                          │
│  Step 1 → Step 2 → Step 3 → Step 4  │
│  (everything runs one-by-one)        │
└──────────────────────────────────────┘
  Time: ████████████████████████

Multi-threaded program (now):
┌──────────────────────────┐
│ Main Thread              │
│  Step 1 → Step 2 → ... → │
└──────────────────────────┘
┌──────────────────────────┐
│ Worker Thread 1          │
│  Task A → Task B → ...   │
└──────────────────────────┘
┌──────────────────────────┐
│ Worker Thread 2          │
│  Task X → Task Y → ...   │
└──────────────────────────┘
  Time: ████ (all parallel!)

Result: More work done in same time ✓

✓ When to Use Threads

  • Your program needs to do multiple things at once (e.g., sensor reading + computation)
  • You have a multi-core CPU and want to use all cores
  • You need to keep a UI responsive while doing background work
  • You want event-driven processing (e.g., fusion thread wakes only when data arrives)

✗ When NOT to Use Threads

  • Your program is single-core or latency-sensitive without parallelism
  • You can solve it with a simple loop or callback
  • You don't need true parallelism (async/await might be simpler)
  • You're unsure about synchronization—threads add complexity!

⚙️Part 2: Creating and Managing Threads

Header: #include <thread>

Basic Example: Create and Join a Thread

// Simple function for a thread to run
void worker() {
    std::cout << "Worker thread running!" << std::endl;
}

int main() {
    // Create a thread, pass function name
    std::thread t(worker);

    // Main thread continues here in parallel
    std::cout << "Main thread running!" << std::endl;

    // Wait for worker to finish (REQUIRED!)
    t.join();

    // Safe to exit now
    return 0;
}

⚠️ Critical Rule: ALWAYS join() or detach()

Before a thread object is destroyed, you must call either:

  • thread.join() — wait for thread to finish
  • thread.detach() — let thread run in background (dangerous!)

Why? Destroying a joinable thread calls std::terminate() and crashes your program!

std::thread Constructor

std::thread(function, arg1, arg2, ...)

Creates and starts a thread immediately. Can pass any callable (function, lambda, functor).

Passing Arguments to Threads

void add(int a, int b) {
    std::cout << a << " + " << b << " = " << (a + b) << std::endl;
}

int main() {
    // Pass arguments to thread
    std::thread t(add, 3, 5);
    t.join();
    return 0;
}

Using Lambdas (Modern C++)

int main() {
    std::thread t([] {
        std::cout << "Lambda thread!" << std::endl;
    });
    t.join();
    return 0;
}

Modern: std::jthread (C++20)

std::jthread automatically joins when destroyed (no need to manually call join()).

int main() {
    std::jthread t([] { std::cout << "Auto-joining!" << std::endl; });
    // t automatically joins here when t goes out of scope ✓
    return 0;
}

🔐Part 3: The Race Condition Problem

❌ Race Condition Example (DANGEROUS!)

int counter = 0;

void increment() {
    for (int i = 0; i < 100000; i++) {
        counter++;  // THIS IS NOT ATOMIC!
    }
}

int main() {
    std::thread t1(increment);
    std::thread t2(increment);

    t1.join();
    t2.join();

    // Expected: 200000, but might be 150000! 🚨
    std::cout << counter << std::endl;
}

Why This Fails

counter++ is not a single CPU instruction. It's actually 3 steps:

  1. Read current value of counter
  2. Add 1
  3. Write back to memory

If threads interleave, one thread's increment can get lost:

Thread 1                    Thread 2                  counter value
Read (counter=5)
                           Read (counter=5)           5
Add 1 (= 6)
Write back (counter=6)                                6
                           Add 1 (= 6)
                           Write back (counter=6)     6  ← OOPS! Should be 7

✓ Solution: Synchronization

Protect shared data so only one thread accesses it at a time. This is called a critical section.

🔒Part 4: Synchronization Primitives

1. Mutex (Mutual Exclusion)

Header: #include <mutex>

What it does: Only one thread can hold a mutex at a time. Others wait.

Basic Usage

#include <mutex>

std::mutex mtx;
int counter = 0;

void increment() {
    for (int i = 0; i < 100000; i++) {
        // Lock before accessing shared data
        mtx.lock();
        counter++;
        mtx.unlock();  // Unlock after
    }
}

⚠️ Problem: Exceptions!

If an exception happens between lock() and unlock(), the mutex stays locked forever (deadlock!).

Better: Use RAII Lock Guards

void increment() {
    for (int i = 0; i < 100000; i++) {
        // RAII: lock acquired in constructor, released in destructor
        std::lock_guard<std::mutex> lock(mtx);
        counter++;
        // lock automatically released here ✓
    }
}

2. Lock Types (RAII Wrappers)

Lock Type Behavior Use Case
lock_guard Locks on creation, unlocks on destruction. Can't unlock early. Simple, scope-based locking. Most common.
unique_lock Locks on creation, unlocks on destruction. Can manually unlock/relock. Need flexibility. Works with condition variables.
shared_lock Multiple readers can hold simultaneously (read-only). Many readers, few writers. Needs shared_mutex.

unique_lock Example (More Control)

std::mutex mtx;

void example() {
    std::unique_lock<std::mutex> lock(mtx);  // Locks here

    std::cout << "Protected section" << std::endl;

    lock.unlock();  // Unlock early if needed
    long_operation();  // Run without lock
    lock.lock();  // Re-lock

    // Automatically unlocks at end of scope
}

3. Atomic Operations (Lock-Free)

Header: #include <atomic>

What it does: Guarantees single-instruction operations. No locks needed!

✓ Atomic Counter (No Mutex!)

#include <atomic>

std::atomic<int> counter = 0;  // Atomic version counter

void increment() {
    for (int i = 0; i < 100000; i++) {
        counter++;  // Safe! Atomic operation, no lock needed
    }
}

int main() {
    {
        std::jthread t1(increment);
        std::jthread t2(increment);
    } // Both threads auto-join here when they go out of scope

    std::cout << counter.load() << std::endl;  // Correctly prints 200000 ✓
    return 0;
}
Atomic Method Description
.load() Read the value (with memory ordering)
.store(val) Write the value (with memory ordering)
++, += Atomic increment/addition
.exchange(val) Swap value and return old one
.compare_exchange(expected, desired) Update only if current == expected (atomic compare-and-swap)

4. Condition Variables (Wait & Notify)

Header: #include <condition_variable>

What it does: Thread waits until another thread signals "condition is ready"

Producer-Consumer Pattern

Producer Thread                Consumer Thread
  Make data
  Notify CV ──────────────→     Wake from sleep
                           Acquire lock
                           Process data
                           Release lock
  Make more data

Example: Data Queue

#include <condition_variable>
#include <queue>

std::queue<int> data_queue;
std::mutex mtx;
std::condition_variable cv;
bool done = false;  // Tells consumer no more data is coming

// Producer: puts data in queue and notifies
void producer() {
    for (int i = 0; i < 10; i++) {
        {
            std::lock_guard<std::mutex> lock(mtx);
            data_queue.push(i);
        }
        cv.notify_one();  // Wake sleeping consumer
    }
    {
        std::lock_guard<std::mutex> lock(mtx);
        done = true;  // No more items will ever be pushed
    }
    cv.notify_one();  // Wake consumer so it can notice 'done'
}

// Consumer: waits for data, then processes
void consumer() {
    while (true) {
        std::unique_lock<std::mutex> lock(mtx);

        // Wait until queue has data OR producer is done (releases lock while waiting!)
        cv.wait(lock, [] { return !data_queue.empty() || done; });

        if (data_queue.empty() && done) {
            break;  // Nothing left, and nothing more coming — exit the loop
        }

        int value = data_queue.front();
        data_queue.pop();
        lock.unlock();

        std::cout << "Processed: " << value << std::endl;
    }
}

✓ Why Not Just Loop & Check?

You could check in a loop, but it wastes CPU (busy-waiting). Condition variables put thread to sleep until signaled—efficient!

📋Part 5: Synchronization Comparison

Primitive Purpose Use When Overhead
std::mutex Exclusive access (one thread at a time) Protecting a shared resource from corruption Medium (lock/unlock cost)
std::shared_mutex Read-write lock (many readers OR one writer) Many readers, few writers (e.g., config file) High (more complex than mutex)
std::atomic Lock-free operations on single values Counters, flags, version numbers (no contention) Low (single CPU instruction)
std::condition_variable Wait for a condition to be true Producer-consumer, waiting for events Low (thread sleeps, doesn't spin)
std::latch (C++20) One-time synchronization point Wait for N threads to reach a point Low (used once)
std::semaphore (C++20) Counter-based access (like N resource slots) Limiting concurrent access to N things Low

⚡Part 6: C++20 Utilities

std::latch (Barrier Synchronization)

What: Threads wait until a counter reaches zero.

Use case: Start all worker threads simultaneously (no partial startup races).

std::latch start_gate(3);  // Wait for 3 threads

void worker(int id) {
    start_gate.arrive_and_wait();  // Decrement counter and wait
    std::cout << "Worker " << id << " GO!" << std::endl;
}

int main() {
    std::jthread t1(worker, 1);
    std::jthread t2(worker, 2);
    std::jthread t3(worker, 3);
    // All 3 threads wait here, then all print "GO!" together ✓
}

std::stop_token (Cooperative Shutdown)

What: Signal threads to stop cleanly (works with jthread).

void worker(std::stop_token stoken) {
    while (!stoken.stop_requested()) {
        // Do work...
    }
    // Clean exit
}

int main() {
    std::jthread t(worker);
    std::this_thread::sleep_for(std::chrono::seconds(5));
    t.request_stop();  // Signal stop (worker exits loop)
    // t automatically joins ✓
}

🎯Part 7: Common Patterns

Pattern 1: Reader-Writer (Shared Mutex)

std::shared_mutex mtx;
Data shared_data;

// Many threads can read simultaneously
void reader() {
    std::shared_lock lock(mtx);  // Shared read lock
    Data copy = shared_data;  // Safe to read
}

// Only one thread can write
void writer() {
    std::unique_lock lock(mtx);  // Exclusive write lock
    shared_data = Data();  // Exclusive access
}

Pattern 2: Thread-Safe Wrapper (RAII)

template<typename T>
class Safe {
    T value_;
    mutable std::mutex mtx_;

public:
    void set(T val) {
        std::lock_guard lock(mtx_);
        value_ = val;
    }

    T get() {
        std::lock_guard lock(mtx_);
        return value_;
    }
};

// Usage:
Safe<int> counter;
counter.set(5);
int val = counter.get();  // Always thread-safe ✓

Pattern 3: Blocking Queue

template<typename T>
class BlockingQueue {
    std::queue<T> q_;
    mutable std::mutex mtx_;
    std::condition_variable cv_;

public:
    void push(T val) {
        {
            std::lock_guard lock(mtx_);
            q_.push(val);
        }
        cv_.notify_one();
    }

    T pop() {
        std::unique_lock lock(mtx_);
        cv_.wait(lock, [this] { return !q_.empty(); });
        T val = q_.front();
        q_.pop();
        return val;
    }
};

⚠️Part 9: Common Pitfalls & How to Avoid Them

❌ Pitfall 1: Forgetting to join()

void bad_example() {
    std::thread t([] { std::cout << "Hello" << std::endl; });
    // CRASH! t is destroyed without joining ❌
}

// Fix:
void good_example() {
    std::jthread t([] { std::cout << "Hello" << std::endl; });
    // Auto-joins ✓
}

❌ Pitfall 2: Deadlock (Circular Waiting)

std::mutex m1, m2;

// Thread 1
void thread1() {
    m1.lock();
    sleep(100);
    m2.lock();  // Waits for m2...
}

// Thread 2
void thread2() {
    m2.lock();
    sleep(100);
    m1.lock();  // Waits for m1...
}
// DEADLOCK! ❌ Each waits for the other

// Fix: Always acquire locks in same order
void fixed_thread1() {
    std::lock(m1, m2);  // Atomic lock both ✓
    std::lock_guard l1(m1, std::adopt_lock);
    std::lock_guard l2(m2, std::adopt_lock);
}

❌ Pitfall 3: Use-After-Free

void bad_example() {
    int* ptr = new int(42);
    std::thread t([ptr] {
        std::this_thread::sleep_for(std::chrono::seconds(1));
        std::cout << *ptr << std::endl;  // ptr might be deleted! ❌
    });
    delete ptr;  // Oops!
    t.join();
}

// Fix: Use shared_ptr or copy by value
void good_example() {
    int value = 42;
    std::thread t([value] {  // Copy captured by value ✓
        std::this_thread::sleep_for(std::chrono::seconds(1));
        std::cout << value << std::endl;
    });
    t.join();
}

❌ Pitfall 4: Spurious Wakeups

// WRONG: CV can wake up without notification!
void bad_wait(std::unique_lock<std::mutex>& lock) {
    cv.wait(lock);  // Might wake without data! ❌
    int value = queue.front();  // CRASH: queue is empty!
}

// CORRECT: Always use predicate
void good_wait(std::unique_lock<std::mutex>& lock) {
    cv.wait(lock, [this] { return !queue.empty(); });  // ✓
    int value = queue.front();
}

✅Part 10: Best Practices Checklist

✓ Dos

  • ✓ Use std::jthread instead of std::thread (auto-joins)
  • ✓ Always use RAII locks (lock_guard, unique_lock)
  • ✓ Use shared_lock for read-heavy workloads
  • ✓ Use atomics for simple counters (no lock contention)
  • ✓ Use condition variables for producer-consumer patterns
  • ✓ Always pass predicates to cv.wait()
  • ✓ Keep critical sections small (minimize lock holding time)
  • ✓ Acquire multiple locks in consistent order (avoid deadlock)
  • ✓ Test with ThreadSanitizer (-fsanitize=thread) and Helgrind

✗ Don'ts

  • ✗ Don't hold locks across I/O operations
  • ✗ Don't acquire a lock inside a lock (nested locks = deadlock risk)
  • ✗ Don't use detach() unless you really know what you're doing
  • ✗ Don't capture pointers by reference in thread lambdas (use shared_ptr)
  • ✗ Don't ignore race conditions ("it works on my machine")
  • ✗ Don't assume atomics are free (still have memory ordering overhead)
  • ✗ Don't use volatile for thread synchronization (it doesn't work!)

🔗Summary: How It All Fits Together

Threading is about:

  1. Creating work units: Use std::jthread to spawn threads
  2. Identifying shared data: Anything accessed by multiple threads
  3. Protecting shared data: Use mutex, atomic, or condition_variable
  4. Synchronizing execution: Coordinate when threads run, wait, and stop
  5. Testing & debugging: Use ThreadSanitizer to find races

The golden rule: Never access shared data without synchronization.
