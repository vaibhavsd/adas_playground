Overview

Day 6 — tracker.hpp — "Objects have memory."

What this file does

Sensors give noisy, single-frame snapshots (a detection is a rumour). The tracker turns a stream of these into a stable list of IDs with position and velocity (a track is a belief), by:
  1. Estimating position and velocity per object with a hand-written Kalman filter.
  2. Matching new detections to existing tracks (nearest-neighbour data association with gating).
  3. Managing identity over time — a track is tentative until enough evidence confirms it, and is dropped after too many misses.
Multi-sensor fusion angle: radar gives Doppler velocity, camera/lidar don't. Radar seeds a track's velocity estimate; all three sensor types then refine position. A track needs hits from 2+ distinct sensor kinds before it's trusted — this is what kills false positives from a single camera shadow or lidar reflection.

Where are tracks stored?

In a single private member of Tracker — there is one map, not one per sensor: 
std::unordered_map<int, Track> tracks_;
int                             next_id_{1};
Every track gets a fresh id from next_id_++ when it's spawned, and the map lives for the lifetime of the Tracker object — one Tracker per whole simulation run (constructed once in main(), line 99).
tracker.hpp:274-277 (private members of Tracker)

How many tracks get created?

There's no fixed count and no "one track per real object" guarantee by construction — it falls out of the association loop, one decision per detection:
  1. Every detection in dets either updates the single nearest existing track (if within gate) or spawns exactly one new track — never both, never zero.
  2. In steady state, a real object that all three sensors can see keeps exactly one track alive, because each new detection lands close enough to the existing track's (Kalman-smoothed) position to fall inside the gate — so it updates rather than spawns.
  3. A track only survives long enough to matter if it keeps getting hit; a one-off false detection spawns a track that racks up misses and gets pruned (misses > max_misses) before ever being confirmed, let alone published.
In short: the number of live tracks in tracks_ is bounded by "distinct detections that were too far from every existing track to associate" — it self-regulates toward roughly one track per real, persistently-detected object, but nothing in the code enforces that count directly.
tracker.hpp:194-230 (Tracker::update)

How is a track affected by "the other sensors"?

There's no per-sensor track state — a Track doesn't know or care which sensor last touched it beyond the sensor_mask bit. Every detection, regardless of origin, competes for the same nearest-track search and (if it gates) updates the same two Kalman1D filters (x and y). Concretely, per detection:
SensorAlways doesSometimes does
Radarupdate_position(pos, r=σ²)update_velocity(vel, radar_vel_var) — only if use_doppler_updates=true (default: false)
Cameraupdate_position(pos, r=σ²)— (no velocity signal at all)
Lidarupdate_position(pos, r=σ²)— (no velocity signal at all)
So a track's velocity estimate mostly comes from the Kalman filter's own position/velocity covariance coupling (position measurements alone let velocity drift toward consistency with observed motion — see the worked example above), seeded initially by radar's Doppler if radar detected it first (spawn(), below). Each sensor also contributes its own measurement noise r = d.sigma² — a confident lidar hit pulls the estimate harder than a fuzzy camera guess (sigma values come from to_detection() in sensors.hpp: lidar 0.3, radar 0.8, camera up to 0.15 × range).

Where is spawning vs. merging logic?

Spawning — a brand-new track from one unmatched detection:
else {
    spawn(d);      // tracker.hpp:228, spawn() defined at tracker.hpp:261
}
"Merging" two sensors' worth of evidence into one track happens implicitly, inside the gated branch of the same loop — it's not a separate step, it's just "the detection updated an existing track instead of spawning a new one": 
if (best != tracks_.end() && geo::distance(...) < gate) {
    Track& t = best->second;
    t.x.update_position(...);   // <- this *is* the fusion: radar's, camera's, and
    t.y.update_position(...);   //    lidar's detections all update the same t
    ...
}
Gap worth knowing about: there is no function anywhere that merges two already-separate Track objects that turn out to represent the same real obstacle. If two tracks ever spawn slightly apart (e.g. two sensors' first detections of a new object landing just outside each other's gate before either track existed), they stay as two independent tracks forever — nothing in Tracker will notice and combine them later. In practice this rarely happens because the default gate (gate_m + 2σ, typically 4–8 m) is generous relative to sensor noise, but it's a real limitation of this implementation, not a design choice documented anywhere in the code.

Kalman1D — predict()

Constant-velocity 1D filter, one instance per axis (x and y, decoupled)

State & the predict step

State is $\mathbf{x} = [p, v]^T$ — position and velocity along one axis. $F$ advances the state by $\Delta t$ assuming constant velocity; $Q$ injects uncertainty for the acceleration we didn't model.
$$ \mathbf{x} = F\mathbf{x}, \qquad P = FPF^T + Q, \qquad F = \begin{pmatrix} 1 & \Delta t \\ 0 & 1 \end{pmatrix} $$
Expanded, this is just:
$$ p \mathrel{+}= v \cdot \Delta t \qquad (\text{velocity itself is unchanged by predict}) $$
Kalman1D::predict, geometry.hpp Mat2 does the P update

Discrete white-noise-acceleration process noise

$q$ is the assumed acceleration variance (m/s²)². This particular $Q$ shape comes from treating unmodeled acceleration as white noise and integrating twice — it's the standard "discrete white noise acceleration" (DWNA) model for a constant-velocity filter.
$$ Q = q \begin{pmatrix} \Delta t^4/4 & \Delta t^3/2 \\ \Delta t^3/2 & \Delta t^2 \end{pmatrix} $$
Kalman1D::predict — d2/d3/d4 are dt², dt³, dt⁴

Kalman1D — update steps

Two update variants; both are the same equations with a different H

Generic Kalman update

$H$ picks out which state component the measurement $z$ observes; $R$ is that measurement's noise variance; $K$ is the Kalman gain (how much to trust the new measurement vs. the existing belief).
$$ \begin{aligned} y &= z - H\mathbf{x} & \text{(innovation)} \\ S &= HPH^T + R & \text{(innovation covariance)} \\ K &= PH^T S^{-1} & \text{(Kalman gain)} \\ \mathbf{x} &= \mathbf{x} + Ky \\ P &= (I - KH)P \end{aligned} $$
With a 2-state filter and a scalar measurement, $S$ is a scalar and "matrix inverse" is a plain division — that's why this file needs no linear-algebra library, just Mat2.

update_position() — $H = [1\ 0]$

Every sensor can report a position, so every detection calls this.
$$ \begin{aligned} S &= P_{aa} + r \\ K_p &= P_{aa}/S, \quad K_v = P_{ca}/S \\ y &= z - p \\ p &\mathrel{+}= K_p\, y, \qquad v \mathrel{+}= K_v\, y \end{aligned} $$
Kalman1D::update_position(z, r)

update_velocity() — $H = [0\ 1]$

Only radar (Doppler) can measure velocity directly — mirror image of the position update.
$$ \begin{aligned} S &= P_{dd} + r \\ K_p &= P_{bd}/S, \quad K_v = P_{dd}/S \\ y &= z - v \\ p &\mathrel{+}= K_p\, y, \qquad v \mathrel{+}= K_v\, y \end{aligned} $$
In practice the codebase doesn't call this by default (use_doppler_updates = false) — see the note in the worked example below for why.
Kalman1D::update_velocity(z, r)

Position uncertainty (σ)

A single scalar summary of how confident the track's position estimate is, combining both axes.
$$ \sigma_{\text{pos}} = \sqrt{\tfrac{1}{2}\left(P^x_{aa} + P^y_{aa}\right)} $$
Track::pos_sigma

Worked example — predict then update

Suppose a track's x-axis filter currently believes:

p = 10.0 m       (position)
v = 2.0 m/s      (velocity)
P = [[1.0, 0.0],
     [0.0, 0.5]]  (covariance)

process noise q = 1.0
dt = 0.1 s

Predict (no measurement yet, just advance time):

$$ p \leftarrow 10.0 + 2.0 \times 0.1 = 10.2 $$
Q = 1.0 * [[dt^4/4, dt^3/2],   = [[0.000025, 0.0005],
           [dt^3/2, dt^2 ]]        [0.0005,   0.01  ]]

P' = F P F^T + Q
   = [[1.005025, 0.0505],
      [0.0505,   0.51  ]]

A new lidar detection arrives: z = 10.35 m, measurement variance r = 0.09 (σ = 0.3 m, lidar's usual sigma).

update_position:

$$ \begin{aligned} S &= 1.005025 + 0.09 = 1.095025 \\ K_p &= 1.005025 / 1.095025 \approx 0.9178 \\ K_v &= 0.0505 / 1.095025 \approx 0.0461 \\ y &= 10.35 - 10.2 = 0.15 \\ p &\leftarrow 10.2 + 0.9178 \times 0.15 \approx 10.338 \\ v &\leftarrow 2.0 + 0.0461 \times 0.15 \approx 2.007 \end{aligned} $$
The filter trusts the new position measurement heavily (gain ≈ 0.92, since its own uncertainty had grown during predict) and nudges velocity up only slightly — even though this was a position-only measurement, the position/velocity covariance term $P_{ca}=0.0505$ lets the correction "leak" into the velocity estimate. That's the whole point of tracking both in one filter instead of two independent ones; the leak is small here because after just one 0.1 s predict step the two axes haven't built up much correlation yet.

Track — one object's belief state

Two Kalman1D filters (x, y) plus lifecycle bookkeeping

Fields

struct Track {
    int      id;
    Kalman1D x, y;           // decoupled per-axis filters
    int      hits{1};
    int      misses{0};
    unsigned sensor_mask{0}; // bit i set <=> SensorKind i has hit this track
    Clock::time_point last_seen;
};
pos() and vel() just read out {x.position(), y.position()} and {x.velocity(), y.velocity()} — the two axes never talk to each other inside the filter itself, only through how detections update both at once.

sensor_mask as a bitmask

Each SensorKind (Radar=0, Camera=1, Lidar=2) owns one bit. A hit from sensor kind $k$ OR-s in bit $k$; counting distinct sensor types that have ever hit this track is just std::popcount(sensor_mask). 
sensor_mask |= 1u << static_cast<unsigned>(d.kind);

  Radar  hit  -> mask = 0b001
  + Lidar hit -> mask = 0b101   (popcount = 2 -> can now confirm)

Tracker::predict_to(now)

Step 1 of the cycle — advance every track's belief to the current time

What happens

On every call after the first, compute $\Delta t$ since the last call and run predict(dt, process_noise) for both axes of every track. The very first call just records now as a baseline — there is nothing to predict from yet.
$$ \Delta t = \text{now} - t_{\text{last}} $$
Tracker::predict_to

Tracker::update(detections) — data association

Step 2 — match each detection to a track, or spawn a new one

Nearest-neighbour matching with gating

For each incoming detection, find the closest existing track by Euclidean distance. Accept the match only if it falls inside a gate — a radius that grows with the detection's own uncertainty, so a fuzzy 40 m camera guess is allowed more slack than a precise lidar hit.
$$ \text{gate} = \text{gate}_m + 2\sigma_{\text{det}} $$
  1. Find best = argmin distance(track.pos(), detection.pos_world) over all tracks.
  2. If distance(best, detection) < gate: update that track's Kalman filters (position always; velocity only if the flag is set and it's a radar detection with Doppler).
  3. Otherwise: spawn() a brand-new tentative track for this detection.
  4. Any track that matched nothing this cycle gets ++misses.
  5. Tracks with misses > max_misses are pruned via std::erase_if.
Tracker::update

Why Doppler doesn't directly update velocity

Radar's Doppler measurement is radial velocity only (speed toward/away from the sensor), not a full 2D velocity vector. Feeding it straight into update_velocity() for both x and y biases the direction estimate — measured in practice to walk predicted obstacles into the wall on curves. So by default (use_doppler_updates = false), Doppler only seeds a new track's initial velocity in spawn(); it never corrects an existing one. A correct fix needs a coupled 4-state filter (noted in the code as Exercise 6.3).

Confirmation logic — track lifecycle

tentative → confirmed → dead

State machine

tentative → confirmed → dead
A track starts tentative the moment any single detection spawns it. It becomes confirmed once both conditions below hold, and is declared dead (and pruned) once it's gone too long without a match.
$$ \text{confirmed} \iff \text{hits} \ge H_{\text{confirm}} \ \wedge\ \operatorname{popcount}(\text{mask}) \ge S_{\text{confirm}} $$
$$ \text{dead} \iff \text{misses} > M_{\max} $$
Default config: confirm_hits = 4, confirm_sensors = 2, max_misses = 15. Requiring 2 distinct sensor kinds is what prevents a single false detector glitch (a camera shadow, a lidar reflection) from becoming a "confirmed" ghost object — it needs a second, independent sensor to agree first.
Tracker::is_confirmed, Tracker::Config

spawn() and prune

Birth and death of tracks

spawn(detection)

A new track is seeded directly from one detection. If the detection carries a velocity (radar only), that seeds $v_0$ and gets a tighter initial velocity variance (radar_vel_var); otherwise velocity starts at zero with a wide variance (25), reflecting "we have no idea yet."
$$ v_0 = \begin{cases} \mathbf{v}_{\text{detection}} & \text{radar} \\ \mathbf{0} & \text{otherwise} \end{cases} \qquad \operatorname{Var}(v_0) = \begin{cases} \sigma^2_{v,\text{radar}} & \text{radar} \\ 25 & \text{otherwise} \end{cases} $$
Position variance seeds from the detection's own $\sigma^2$ — a confident lidar hit starts the new track's position filter more confident than a fuzzy camera guess would.
Tracker::spawn

Pruning

After every update(), tracks whose miss counter has exceeded max_misses are removed with C++20's std::erase_if — no manual erase-while-iterating dance needed on the underlying unordered_map.
